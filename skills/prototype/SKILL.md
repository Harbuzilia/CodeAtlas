# Prototype Skill

> Прототип = одноразовый код, отвечающий на ОДИН вопрос. Вопрос определяет форму.
> Адаптировано из mattpocock/skills (MIT).

## Зачем

Спорить о state-машине или раскладке в тексте — медленно и неточно. Прототип за 15 минут закрывает вопрос доказательством, которое можно потрогать.

## Ветка 1: логика / state-модель

Вопрос вида «правильно ли ведёт себя state-машина / алгоритм / поток?»:
- Один самодостаточный HTML-файл (`.tmp/prototype/<slug>/LOGIC.html`): модель + свободные ручки (кнопки/инпуты меняют состояние) + пошаговый guided-обход ключевого сценария.
- Доступен нетехническим людям: открыл в браузере — потрогал (Windows: двойной клик).

## Ветка 2: look-and-feel

Вопрос вида «какая раскладка/подача лучше?»:
- Один роут с 3-4 РАДИКАЛЬНО разными вариантами, переключение через `?v=1..4` (search-параметр) + плавающая панель внизу для переключения.

Неоднозначный вопрос → выбери ветку по окружению (бэкенд-модуль → логика; страница/компонент → UI) и заявь допущение в ответе.

## Общие правила

1. Прототип живёт в `.tmp/prototype/<slug>/` (gitignored — не попадает в main и не требует чистки репо).
2. Запуск тривиален: одна команда или двойной клик по HTML.
3. Без персистентности по умолчанию (in-memory); вопрос реально про БД — явно помеченный scratch-store.
4. Без полировки: без тестов, без абстракций, минимальная обработка ошибок.
5. После каждого действия/переключения показывай ПОЛНОЕ состояние — изменения должны быть видны.
6. **Финал**: ответ на вопрос → решение переносится в настоящий код (в нормальном месте, с тестами); вердикт — в отчёт/ADR одной строкой («прототип подтвердил X»); сами файлы прототипа выбрасываются (в .tmp, ничего чистить не надо). Main получает только решение.

## Когда НЕ надо

- Вопрос «сделает ли это оптимизацию» — это benchmark, не прототип.
- Поведение уже доказуемо тестом/типами — пиши тест.
