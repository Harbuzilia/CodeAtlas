# Domain Modeling Skill

> Предметная область как код: термины проверяются, а не предполагаются.
> Адаптировано из mattpocock/skills (MIT).

## Зачем

Половина багов — «одно слово, два смысла». Глоссарий дисциплинирует: термин, не выдержавший edge-кейс, ловится на этапе разговора, а не в проде.

## Файлы

- **`context/domain/CONTEXT.md`** — глоссарий: термин → определение → связи с другими терминами. Создаётся лениво (только когда есть что записать).
- **Мульти-модульные проекты**: `context/domain/MAP.md` указывает на `context/domain/<модуль>/CONTEXT.md`.
- **ADR** — в `docs/adr/NNN-title.md` (конвенция architect-агента), только если решение: трудно обратимо И удивительно без контекста И рождено реальным trade-off. Иначе — строка в CONTEXT.md.

## Поведение в сессии

1. **Оспаривай термины**: термин пользователя конфликтует с глоссарием → назови конфликт и предложи канон, не подстраивайся молча.
2. **Затачивай расплывчатое**: «документ», «заявка», «аккаунт» без границы — потребуй определение или предложи своё с edge-кейсами.
3. **Стресс-тест связей**: к каждой связи сформулируй конкретный edge-кейс («аккаунт может иметь 0 заказов? а 2 подписки на один тариф?»). Непроверяемая связь — не связь.
4. **Сверяйся с кодом**: утверждение о предмете проверяется по коду/тестам; расхождение — вопрос или ADR, не фантазия.
5. **Записывай сразу**: термин устоялся → обнови CONTEXT.md немедленно, до финального отчёта.
6. **CONTEXT.md — только глоссарий**: без имплементации, истории и решений (это в ADR/коде).

## Когда НЕ надо

- Один-off скрипт без повторного использования терминов.
- Термин уже покрыт глоссарием и не оспаривается — не перегенерируй.
