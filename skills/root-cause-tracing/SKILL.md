# Root Cause Tracing Skill

> Симптом — это указатель, не место ремонта. Ищи точку, где решение стало неверным.
> Адаптировано из ядра obra/superpowers (MIT).

## Зачем

Ошибка проявляется там, где данные стали неправильными, а рождается раньше. Патч в точке падения лечит один путь; причина плодит пути. Цепочка «симптом → данные → источник» находит точку рождения бага.

## Методы (выбирай по ситуации)

### 1. Пять «Почему» (для логических/процессных багов)
Симптом → «почему?» → ответ-факт → снова «почему?» — до неперемещаемой причины (той, что не «потому что код так написан», а «потому что решение/контракт таков»).
- Каждый ответ — проверяемый факт, не догадка. 3-5 уровней хватает; 8+ — ты уходишь в философию.

### 2. Бисекция изменений (для регрессий)
- Симптом появился между «работало» и «упало»: `git bisect` (или ручной halving по коммитам).
- Если регрессия плавающая (не коммит) — бисектируй ДАННЫЕ/конфиги/окружение тем же halving.

### 3. Археология (для «всегда так было»)
- `git log -p -- <файл>` — кто и зачем ввёл поведение; сообщение коммита и связанный issue объясняют намерение.
- Найденный интент решает: фиксить код (интент верен) или менять контракт (интент устарел).

### 4. Трассировка данных (для порчи данных)
- От симптома вверх по потоку: где значение ещё правильное, а где уже нет — граница и есть место бага.
- Проверяй границы слоёв: сериализация, парсинг, стык систем, таймзоны, кодировки (UTF-8/CP1251 на Windows).

## Правила

- Причина записана одной фразой + доказательство (репро/лог/коммит). Нет доказательства — это гипотеза, а не причина.
- Фикс в точке причины; если точка вне твоего scope — верни находку с рекомендацией, не лати внутри.
- После фикса — поиск соседних жертв той же причины: где ещё используется сломанный путь?

## Чеклист

- [ ] Причина названа фразой и доказана
- [ ] Фикс применён в точке причины, не симптома
- [ ] Соседние пути от той же причины проверены
- [ ] Интент автора понят (если поведение старое)
