# Test-Driven Development Skill

> RED → GREEN → REFACTOR. Тест определяет поведение; код догоняет тест.
> Адаптировано из ядра obra/superpowers (MIT).

## Зачем

Код, написанный до теста, проверяет себя сам («я так и думал»). Упавший тест сначала — это контракт: ты обязан написать ровно то поведение, которое требовалось, и не больше.

## Цикл (строго)

### RED — тест сначала, он обязан упасть
1. Один тест на одно поведение (positive или negative сценарий).
2. Запусти тест: он должен упасть **по правильной причине** (assertion/exception по фиче, а не ImportError/опечатка).
3. Упал не по той причине → тест ещё не готов, чини тест.

### GREEN — минимальный код до зелёного
- Ровно столько кода, чтобы тест прошёл. Без «заодно», без будущих фич, без лишних абстракций.
- Прогнал — зелёный? Перейди к рефакторингу. НЕ добавляй соседнее поведение в этом цикле.

### REFACTOR — чистка под защитой зелёного
- Дубли, нейминг, вынос хелперов — только при зелёных тестах, прогон после каждого шага чистки.
- Изменил поведение = это новый RED-цикл, не рефакторинг.

## Дисциплина объёма (анти-перетестирование)

- Тесты на затронутое поведение, не на весь файл подряд.
- Полный suite — 2 прогона на задачу: первичный и финальная верификация (см. [SCOPE] у tester).
- Один edge-case = один тест; не плоди варианты одного сценария.

## Анти-паттерны (STOP-сигналы)

- Код написан, тест «потом допишу» — RED пропущен, контракт потерян.
- Тест написан под уже работающим кодом — он ничего не ловит, только подтверждает.
- GREEN «с запасом»: реализовано больше, чем требует тест.
- Менять assertion, чтобы тест прошёл (мягче условие), вместо правки кода.
- Тест зависит от порядка/порядка прогонов или от живой сети/времени.

## Чеклист

- [ ] Каждый новый тест сначала падал (по правильной причине)
- [ ] Код минимальный, без «заодно»
- [ ] REFACTOR-шаги под зелёным прогоном
- [ ] Отрицательные сценарии покрыты (ошибки, границы, пустые входы)
