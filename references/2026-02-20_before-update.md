## Executive summary

- Текущая версия функционально богаче: многоуровневая архитектура агентов, расширенный набор skills/workflows/commands, продвинутый memory stack.
- Новая версия архитектурно чище и проще в сопровождении: один центральный оркестратор, строгая делегация, runtime-валидация и governance-пайплайн.
- Основной риск прямого апдейта: потеря пользовательских возможностей (кастомные агенты, skills, workflows, MCP для памяти `cipher` и `claude-context`).
- Основной риск оставаться на текущем состоянии: рост операционной сложности, дрейф документации и конфигов, потенциальная хрупкость поддержки.
- Рекомендуемая стратегия: **adopt core governance + preserve custom runtime** (взять сильные практики новой версии, не ломая кастомный контур текущей).

## Текущее состояние (базовая версия)

### Сильные стороны

1. Богатая декомпозиция ролей: `agent/core`, `agent/planning`, `agent/research`, `agent/build`, `agent/subagents`, `agent/orchestrator`, `agent/meta`.
2. Гибкая оркестрация: роутинг, workflow-builder, отдельные управленческие сценарии.
3. Сильный memory-контур: `cipher` (long-term), `claude-context` (semantic/code context), `memory` graph.
4. Развитая экосистема расширений: большое число skills, commands, workflows и контекстных стандартов.
5. Наличие governance-слоя в `AGENTS.md` и `instructions.md` (качество, безопасность, перформанс, token economy).

### Слабые стороны

1. Высокая сложность сопровождения: много уровней и точек конфигурации.
2. Дрейф между документацией и runtime-состоянием (часть docs устарела относительно фактической конфигурации).
3. Дублирование и риск рассинхронизации конфигов (например, несколько `dcp.jsonc`).
4. Потенциальные policy-конфликты: строгие текстовые правила vs permissive runtime-настройки.
5. Труднее проводить безопасные апдейты из-за масштаба кастомизаций.

## Целевая новая версия (Opencode1)

### Сильные стороны

1. Упрощенная архитектура: единый центр оркестрации (`agents/openagent.md`).
2. Ясный governance-подход: валидаторы, smoke-проверки, режимная маршрутизация.
3. Ниже операционная стоимость: меньше сущностей, меньше связей, проще onboard/support.
4. Более предсказуемый runtime при соблюдении инвариантов в `opencode.json`.

### Слабые стороны

1. Снижение функциональной гибкости и глубины специализации агентов.
2. Отсутствуют критичные для текущего процесса memory MCP-интеграции (`cipher`, `claude-context`).
3. Нет полноценного слоя для пользовательских кастомизаций на уровне агентов/skills/workflows.
4. Есть признаки рассинхронизации runtime и metadata (пример: runtime-агент есть, в registry не отражен).
5. Часть контента сохраняет legacy-следы (исторические ссылки/путь-структура).

## Ключевые принципы обновления

1. **Не делать full replace** текущего конфига на Opencode1.
2. **Сохранить пользовательское ядро**: собственные агенты, skills, workflows, MCP памяти.
3. **Переносить только зрелые практики** из Opencode1: runtime-валидацию, governance-checks, mode discipline.
4. **Разделить core и custom слои** через явный namespace и правила совместимости.
5. **Все изменения обратимы**: поэтапно, с проверками после каждого шага.

## План обновления (поэтапно)

## Фаза 0 - Freeze и инвентаризация

- Зафиксировать текущий baseline: структура `agent/`, `skill/`, `command/`, `.agent/workflows/`, `context/`, MCP секции в `opencode.json`.
- Отметить обязательные к сохранению кастомные компоненты: `cipher`, `claude-context`, связанные skills и команды.
- Подготовить mapping-таблицу `current -> target -> decision (adopt/adapt/keep)`.

## Фаза 1 - Governance import (без функциональных удалений)

- Перенести и адаптировать валидаторы и smoke-скрипты из Opencode1 в текущий проект.
- Согласовать единый source of truth для runtime (`opencode.json`) и metadata.
- Нормализовать policy-правила (исключить противоречия текстов и реальных permissions).

## Фаза 2 - Архитектурная стабилизация

- Ввести четкое разделение: `core` (upstream-like) и `custom` (ваши расширения).
- Устранить дубли/рассинхроны конфигов (включая DCP-конфиги), оставить один канонический путь.
- Проверить целостность маршрутизации и делегации после нормализации.

## Фаза 3 - Интеграция лучших практик Opencode1

- Добавить mode-driven execution дисциплину там, где это дает предсказуемость.
- Подтянуть устойчивые элементы governance из `validate-runtime-governance.mjs`.
- Сохранить/переиспользовать только те упрощения, которые не ломают custom-memory и custom-workflow.

## Фаза 4 - Документация и эксплуатация

- Обновить архитектурные документы: фактическая структура, SoT, политика расширения.
- Зафиксировать правила добавления новых агентов/skills/workflows/MCP без drift.
- Ввести регулярный health-check: validate + smoke перед каждым крупным изменением.

## Риски и меры снижения

1. Потеря custom-функционала при апдейте -> запрет full replace, только selective merge.
2. Поломка memory-сценариев -> отдельные тесты на `cipher`/`claude-context` и fallback-поведение.
3. Рассинхронизация runtime/metadata -> обязательные проверки целостности в CI/локальном preflight.
4. Растущая сложность после merge -> формализация core/custom boundaries и удаление дублирования.
